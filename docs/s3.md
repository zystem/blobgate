# Use the S3 door

How-to page. The S3 door lets the tools that speak S3 (the AWS CLI, `s3cmd`, `rclone`, the SDKs) read and write the objects of a tenant. What it answers and what it does not: [s3-reference.md](s3-reference.md).

You need a running module with a store ([../README.md](../README.md)) and the secret of a tenant (`BLOBGATE_TENANTS`).

1. Turn the door on with a port (it is off by default). In the environment of the module:

   ```bash
   BLOBGATE_S3_PORT=18093
   ```

   The module says nothing more at start; the door answers on that port at once. Serve it over TLS like the other ports (`BLOBGATE_TLS_CERT_FILE`) when it leaves the cluster: the signature protects a call, not the bytes.

2. Make the key pair of the tenant. The access key is the name of the tenant; the secret key is made from the tenant's secret, and is not that secret:

   ```bash
   blobgate s3-key acme the-secret-of-acme
   ```

   ```text
   access key: acme
   secret key: 1d0c...e5a2
   ```

   (The secret key is 64 hexadecimal characters; it is cut here.)

3. Point the tool at the door. The bucket is the name of a **store** (the operator makes the stores; a tool cannot make a bucket). Use path-style addresses (`http://host:18093/bucket/key`), which is what an address with a port gives.

   The AWS CLI:

   ```bash
   export AWS_ACCESS_KEY_ID=acme AWS_SECRET_ACCESS_KEY=1d0c...e5a2 AWS_DEFAULT_REGION=us-east-1
   aws --endpoint-url http://127.0.0.1:18093 s3 cp big.bin s3://media/docs/big.bin
   aws --endpoint-url http://127.0.0.1:18093 s3 ls s3://media/docs/
   aws --endpoint-url http://127.0.0.1:18093 s3 sync s3://media/docs/ ./docs
   ```

   ```text
   upload: ./big.bin to s3://media/docs/big.bin
   2026-11-14 02:43:11   30000000 big.bin
   download: s3://media/docs/big.bin to docs/big.bin
   ```

   `s3cmd` (a file `s3cfg` with `access_key`, `secret_key`, `host_base = 127.0.0.1:18093`, `host_bucket = 127.0.0.1:18093`, `use_https = False`); its multipart size must be 8 MiB or less:

   ```bash
   s3cmd -c s3cfg --multipart-chunk-size-mb=8 put big.bin s3://media/s3cmd/big.bin
   ```

   ```text
   upload: 'big.bin' -> 's3://media/s3cmd/big.bin' (30000000 bytes in 0.3 seconds, 111.62 MB/s) [1 of 1]
   ```

4. Set the size of a part to 8 MiB or less when the tool sends big objects in parts. A part larger than 8 MiB is refused with the words that say what to set (`a part is at most 8388608 bytes (8 MiB); set the size of the parts of the tool to 8 MiB or less`).

   * AWS CLI: its default (8 MB) works; `aws configure set default.s3.multipart_chunksize 8MB` states it
   * SDK for Go (`manager.Uploader`): `PartSize` of 8 MiB or less (its default, 5 MiB, works)
   * `s3cmd`: `--multipart-chunk-size-mb=8` (its default, 15, is refused)
   * the MinIO client `mc`: `mc put --part-size 8MiB` (its default, 16 MiB, is refused); `mc cp --disable-multipart` sends one request
   * `rclone`: its default (5 MiB) works, and it sends an object under 200 MiB in one request; for a bigger one keep `--s3-chunk-size` at 8M or less
   * SDK for Ruby: `upload_file` (its default, 5 MiB, works); for a copy in parts, `copy_to(..., multipart_copy: true, min_part_size: 8 * 1024 * 1024)` (its default, 50 MiB, is refused)
   * the SDKs of JavaScript (`lib-storage`, default 5 MiB), Java (the transfer manager), Python (boto3, 8 MiB), PHP (`MultipartUploader`, `part_size` 8 MiB) and .NET (`TransferUtility`, `PartSize` 8 MiB): the defaults or 8 MiB work

An address that is signed in advance (`aws s3 presign`) works for reads and writes for as long as it says. A call whose signature does not match is refused with `SignatureDoesNotMatch`: the usual causes are a wrong secret key (use the one `s3-key` prints, not the secret of the tenant), a clock more than 15 minutes off,
and an address that is not path-style.

Each also begins three uploads, lists them (whole, and in pages of one by the markers) and aborts them. All passed after two faults were found and fixed (below). With the AWS CLI `s3api list-multipart-uploads` shows the uploads that were begun, and `rclone backend cleanup` (rclone 1.60.1, `-o max-age=0s`) removed them (the list was empty after). **Over TLS** (2026-11-18, `BLOBGATE_TLS_CERT_FILE` with a self-signed certificate for `127.0.0.1`): the same scripts of boto3 (both versions), JavaScript and Java passed, with the certificate trusted as each SDK is told to (`AWS_CA_BUNDLE` and `SSL_CERT_FILE` for Python, `NODE_EXTRA_CA_CERTS` for Node, a trust store in `-Djavax.net.ssl.trustStore` for Java), presigned addresses included; the AWS CLI copied 25 MB up, in the store and back, identical, and `rclone` (`--ca-cert`) copied, `check`ed (the MD5 matched) and read back identical. Without the certificate trusted the AWS CLI said `CERTIFICATE_VERIFY_FAILED` and rclone `certificate signed by unknown authority`; plain `http://` to the port is answered `400` and does not reach the door. **The SDK for C++** (2026-11-22, `aws-sdk-cpp` 1.11.935 built in Docker, `tools/sdk-check/cpp`, plain `http://`, a mirror of two local nodes): one byte with a type and metadata, 30 MB through the `TransferManager` in parts of 8 MiB (the default checksum of the SDK, CRC32 in a trailer, is accepted) and back, identical, the ETag of the object `"...-4"`, a range across a block border, CopyObject, a listing, deletes: all 19 steps passed at the first run. **The SDK for Swift** (2026-11-22, `aws-sdk-swift` 1.8.33 with Swift 6.1 on Linux in Docker, `tools/sdk-check/swift`; Swift 6.0 crashed in SwiftPM while reading the package): one byte with a type and metadata, 30 MB in four parts of 8 MiB by hand (the default checksum of the SDK is sent), the ETag `"...-4"`, the object back identical, a range across a block border, CopyObject, a listing and the deletes: all 11 steps passed at the first run. Not run: the SDK of Swift on a platform of Apple, `TransferManager` of the Swift SDK (it has none), a presigned address of Signature Version 2 (refused: see the note), a certificate of a public authority and a host name that is not an address, a current MinIO, or a store of a cloud (AWS S3, a CDN's). Ceph was run as a node of a store, not as a client: see [status.md](status.md).

Found by those runs: the names of the metadata went out as `X-Amz-Meta-Owner` (boto3 gave back `Owner` for what was written as `owner`; S3 sends them in lower case, and so does the door now), and a listing of nothing had no `KeyCount` (the Java SDK reads it as null and fails; it is `0` now). **A note for boto3:** its default for a presigned address on a custom endpoint is Signature Version 2, which the door refuses with 403; make the client with `Config(signature_version="s3v4")`.
